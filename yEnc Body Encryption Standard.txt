SPECIFICATION: yEnc Body Encryption Standard
Version: 1.0
Date: 2026-09-25
Author: Independent Specification

Status: Frozen Wire Contract (v1.0)
Category: Standards Track

Abstract:
This document defines a reversible encryption scheme for binary data
in yEnc-encoded blocks used in Usenet transfers. The scheme encrypts
the raw binary data before yEnc encoding using XChaCha20-Poly1305
authenticated encryption, ensuring both confidentiality and integrity
of the transmitted data.

1. Scope

This specification describes the method to encrypt binary data before
yEnc encoding while maintaining:
  - Standard yEnc structure and compatibility
  - Authenticated encryption with integrity protection
  - Deterministic key/nonce derivation from password
  - Clear indication of encryption through yEnc control lines
  - Full compatibility with existing yEnc parsers

It is intended for use in binary file uploads where the actual file
content needs to be encrypted while maintaining yEnc transport
compatibility and providing cryptographic authentication.

----------------------------------------------------------------------
2. Definitions

  yEnc Block:
    A text segment beginning with "=ybegin" and ending with "=yend".

  yEnc Control Line:
    Any line within a yEnc block that begins with "=y" (such as
    "=ybegin", "=ypart", "=yend", or "=yencryption").

  Data Line:
    Any line within a yEnc block that does not begin with "=y"
    (contains the actual encoded binary data).

  Binary Payload:
    The original binary file data before any encryption or yEnc
    encoding.

  Encrypted Payload:
    The binary data after XChaCha20-Poly1305 encryption, including
    the authentication tag.

  segmentIndex:
    An unsigned 32-bit integer in the range 1..=4294967295 carried
    explicitly as the segmentIndex attribute on each NZB <segment>
    element. It provides unique nonce values for every segment across
    the upload session without file-boundary arithmetic.

----------------------------------------------------------------------
3. Processing Procedure

Encryption Input: Binary file data, password, and segmentIndex assigned
to the corresponding NZB <segment> record.

Encryption Steps:

1. Read the binary file data (binary payload).
2. Derive encryption key and nonce using segmentIndex assigned to this
   segment (see Section 4).
3. Encrypt the binary payload using XChaCha20-Poly1305.
4. Extract the authentication tag from the encrypted output.
5. Apply standard yEnc encoding to the ciphertext only (without tag).
6. Insert "=yencryption" control line after the "=ybegin" line
   containing cipher type and authentication tag.
7. Construct complete yEnc block with encrypted data.

Decryption Input: Validated NZB segment record, password from the NZB,
and fetched article body.

Decryption Steps:

1. Parse yEnc block to extract encryption parameters from
   "=yencryption" line.
2. Apply standard yEnc decoding to retrieve encrypted payload.
3. Derive decryption key and nonce using segmentIndex obtained from the
   corresponding NZB segment element.
4. Decrypt and authenticate using XChaCha20-Poly1305.
5. Verify authentication tag and output original binary data.

----------------------------------------------------------------------
4. Encryption Algorithm

Algorithm: XChaCha20-Poly1305 (RFC 8439 Extended)

Parameters:
  - Cipher: XChaCha20 (256-bit key, 192-bit nonce)
  - Authentication: Poly1305 (128-bit tag)
  - Salt: Random 16-byte value (use cryptographically secure RNG)
  - Key derivation: Argon2id(password, salt, time=1, memory=64MB,
    threads=4, 256-bit output)
  - Nonce: HMAC-SHA256(key, "yenc-body nonce" ||
    uint32_be(segmentIndex))[0:24]
    where segmentIndex is the unsigned 32-bit integer serialized in the
    NZB segmentIndex attribute and encoded as a 4-byte unsigned integer
    in big-endian order (uint32_be, network byte order).

Procedure:

  a. Generate salt = Random 16-byte value (once per upload session,
     use cryptographically secure RNG)
  b. Derive key = Argon2id(password, salt, time=1, memory=64MB,
     threads=4, 256-bit output)
  c. Derive nonce = HMAC-SHA256(key, "yenc-body nonce" ||
     uint32_be(segmentIndex))[0:24]
     The message input to HMAC-SHA256 is an exact 19-byte sequence:
     - Bytes 0..14 (15 bytes): ASCII prefix "yenc-body nonce"
       (0x79 0x65 0x6e 0x63 0x2d 0x62 0x6f 0x64 0x79 0x20 0x6e
        0x6f 0x6e 0x63 0x65)
     - Bytes 15..18 (4 bytes): uint32_be(segmentIndex), serialized
       as a fixed 4-byte unsigned integer in big-endian order and
       matching the corresponding NZB segmentIndex attribute
       (network byte order: (segmentIndex >> 24) & 0xFF,
        (segmentIndex >> 16) & 0xFF, (segmentIndex >> 8) & 0xFF,
        segmentIndex & 0xFF).
     The first 24 bytes (digest[0..24]) of the resulting 32-byte
     HMAC-SHA256 digest are extracted as the 192-bit nonce for
     XChaCha20.
  d. Encrypt binary payload using XChaCha20-Poly1305 with derived
     key and nonce, producing ciphertext and 128-bit authentication
     tag.
  e. Apply yEnc encoding to the ciphertext only (excluding the tag).
  f. Insert "=yencryption cipher=XChaCha20-Poly1305 salt=<hex_salt> tag=<hex_tag>"
     control line after "=ybegin" line, where <hex_salt> is the
     16-byte salt and <hex_tag> is the 128-bit authentication tag.

The yEncryption control line format:
  =yencryption cipher=XChaCha20-Poly1305 salt=<32_hex_chars> tag=<32_hex_chars>

Where the control line is a canonical single line (no line wrapping),
the first <32_hex_chars> is the 16-byte salt, and the second
<32_hex_chars> is the 128-bit authentication tag, both formatted in
lowercase hexadecimal characters.

----------------------------------------------------------------------
5. Decryption Algorithm

Input: Fetched yEnc block with encrypted binary data, password from the
NZB, and segmentIndex obtained from the corresponding NZB segment
element.

Steps:

1. Parse yEnc block to locate "=yencryption" control line.
2. Extract cipher type, salt, and authentication tag from the control line.
3. Verify cipher is "XChaCha20-Poly1305".
4. Apply yEnc decoding to data lines to retrieve encrypted payload.
5. Derive key and nonce using the extracted salt, password, and
   segmentIndex obtained from the NZB segment element, including
   big-endian uint32_be serialization of segmentIndex.
6. Decrypt using XChaCha20-Poly1305 with derived parameters.
7. Verify authentication tag matches the tag from the control line.
8. Output decrypted binary data on successful authentication.

Authentication failure MUST result in complete decryption failure
with no partial data output. Decoders and download clients MUST NOT
release, write to disk, or buffer unauthenticated plaintext or
ciphertext to subsequent pipeline stages when authentication fails.

----------------------------------------------------------------------
6. Length Properties

- Encrypted binary data has the same size as original (authentication
  tag is stored in control line, not in data).
- yEnc encoding adds standard yEnc overhead (~2% typical expansion).
- One additional "=yencryption" control line is added to the yEnc
  block.
- Overall expansion is approximately 2% plus one control line with
  32-character hex tag.
- File size in yEnc headers reflects the ciphertext size (same as
  original).

----------------------------------------------------------------------
7. Security Considerations

- XChaCha20-Poly1305 provides both confidentiality and authenticity.
- Unique nonces per segmentIndex prevent nonce reuse across segments.
- Argon2id with random salts provides strong protection against both
  brute-force and rainbow table attacks.
- Random salt per upload session ensures unique keys even for
  identical passwords across different uploads.
- Deterministic nonce derivation eliminates nonce storage
  requirements.
- Authentication tag prevents tampering and provides integrity
  verification.
- Failed authentication MUST abort decryption completely with no
  partial or unauthenticated data output released to disk or
  subsequent processing stages.
- The scheme provides both confidentiality and integrity, unlike
  format-preserving approaches.
- segmentIndex is public metadata carried in the NZB; it does not
  require confidentiality.
- Modifying segmentIndex derives an incorrect nonce and causes
  Poly1305 tag verification to fail with zero plaintext output.
- Subject lines and file ordering have no cryptographic meaning; full
  and per-article subject obfuscation does not affect decryption.

8. NZB File Requirements

An NZB 1.1 document accompanying encrypted uploads MUST specify
encryption metadata according to the following rules:

XML Extension:
Each <segment> element under <segments> within <file> carries an
unqualified, case-sensitive segmentIndex attribute:

  <segment bytes="750000" number="1" segmentIndex="1">article-1@example.com</segment>

Attribute Specification:
- Attribute name: segmentIndex (exact case-sensitive ASCII string).
- Range: unsigned 32-bit integer from 1 to 4294967295 (1..=4294967295).
- Formatting: shortest ASCII decimal representation (digits 0-9 only).
  Implementations MUST reject zero, leading zeroes, signs, whitespace,
  non-decimal characters, non-digits, and values exceeding 4294967295.

Coexistence with Standard Attributes:
The number attribute represents the 1-based part number within the file.
The segmentIndex attribute represents the session-wide encryption index.
Both attributes MUST be written; segmentIndex does not replace number.

Producer Requirements:
For an encrypted upload, the NZB writer MUST:
1. Add segmentIndex to every <segment> in the upload session.
2. Serialize it as the shortest ASCII decimal representation of an
   integer in the range 1..=4294967295.
3. Ensure each encrypted article has a unique value within the upload
   session.
4. Assign indices continuously from 1 when creating a complete new
   upload.
5. Preserve an article's assigned index across retries, reposts,
   resume, NZB regeneration, and queue operations.
6. Continue writing the standard number attribute.

Stored article identity is authoritative. A producer MUST NOT derive an
existing article's index again after files or segments are reordered.

Consumer Requirements:
An encryption-aware NZB reader MUST:
1. Parse and strictly validate segmentIndex whenever present.
2. Reject zero, leading zeroes, signs, whitespace, non-digits, and
   values exceeding 4294967295.
3. Reject duplicate segmentIndex values in the same NZB.
4. Keep the index attached to the same Message-ID through retries,
   persistence, queue reordering, splitting, and restart.
5. Use the explicit index for body nonce derivation.
6. Reject an encrypted article whose NZB segment lacks a valid index.
7. Treat authentication failure as provider corruption only after the
   NZB identity has passed validation.

Consumers SHOULD accept non-contiguous subsets. This permits a valid
subset of an original NZB to retain the original cryptographic
identities. A consumer MUST NOT renumber such a subset.

Decoupling of Subjects and File Order:
Under this extension:
- The <file subject> has no cryptographic meaning.
- The NNTP Subject header has no cryptographic meaning.
- XML file order has no cryptographic meaning.
- XML segment order has no cryptographic meaning.
- [N/M] file counters are optional presentation metadata.

Password Metadata:
The NZB file CAN include the encryption password as a meta tag:
  <meta type="password">your_encryption_password</meta>
This allows download clients to automatically decrypt the binary data.

----------------------------------------------------------------------
9. Interoperability Notes

- Standard yEnc parsers will process encrypted blocks normally,
  ignoring the "=yencryption" control line.
- Decryption-aware tools must recognize and parse the "=yencryption"
  line to enable decryption.
- The encrypted data appears as normal yEnc-encoded binary data to
  non-aware parsers.
- File reconstruction works with standard yEnc tools, producing
  encrypted files that require separate decryption.

10. Example

Input binary data: [18 bytes: 0x48656C6C6F20576F726C642E747874FF]
Password: "test123"

Corresponding NZB segment XML:

  <segment bytes="18" number="1" segmentIndex="1">article-1@example.com</segment>

segmentIndex=1 is obtained from the NZB segmentIndex attribute.

Derived parameters:
- salt: Random 16-byte value = 1a2b3c4d5e6f7890abcdef1234567890
- key: Argon2id("test123", salt, time=1, memory=64MB, threads=4,
  256-bit)  
- nonce: HMAC-SHA256(key, "yenc-body nonce" || uint32_be(1))[0:24]
  (where uint32_be(1) = 0x00 0x00 0x00 0x01)

Encryption:
- XChaCha20-Poly1305 encryption produces 18-byte ciphertext and
  128-bit authentication tag
- Authentication tag: a1b2c3d4e5f6789a0b1c2d3e4f567890

yEnc encoded output:

  =ybegin line=128 size=18 name=file.bin
  =yencryption cipher=XChaCha20-Poly1305 salt=1a2b3c4d5e6f7890abcdef1234567890 tag=a1b2c3d4e5f6789a0b1c2d3e4f567890
  <yEnc-encoded ciphertext data lines>
  =yend size=18

Decryption Processing:
1. Parse "=yencryption" line to extract salt and authentication tag
2. yEnc decode data lines to get 18-byte ciphertext
3. Derive key/nonce using extracted salt and segmentIndex=1 obtained
   from the NZB segment attribute (using uint32_be(1))
4. Decrypt ciphertext using XChaCha20-Poly1305 with tag from
   control line
5. Verify authentication during decryption process
6. Output original 18-byte binary data on success

----------------------------------------------------------------------
11. Summary

This Standard describes authenticated encryption using XChaCha20-
Poly1305 applied to binary data before yEnc encoding, producing
encrypted messages that:
  - Encrypt the actual file content with strong authentication
  - Maintain full yEnc structure compatibility  
  - Provide both confidentiality and integrity protection
  - Use deterministic key/nonce derivation from passwords
  - Include clear encryption indicators in yEnc control lines
  - Remain compatible with standard yEnc processing tools

This approach provides comprehensive protection of binary file content
while maintaining transport compatibility and providing cryptographic
guarantees against both eavesdropping and tampering.

This draft defines the canonical processing rules for interoperability
between implementations.
