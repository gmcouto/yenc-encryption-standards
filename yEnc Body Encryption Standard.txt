SPECIFICATION: yEnc Body Encryption Standard
Version: 1.1
Date: 2026-10-01
Author: Independent Specification

Status: Experimental Wire Contract (v1.1)
Category: Standards Track

Abstract:
This document defines a reversible encryption scheme for binary data
in yEnc-encoded blocks used in Usenet transfers. The scheme encrypts
the raw binary data before yEnc encoding using XChaCha20-Poly1305
authenticated encryption, ensuring both confidentiality and integrity
of the transmitted data.

----------------------------------------------------------------------
1. Scope

This specification describes the method to encrypt binary data before
yEnc encoding while maintaining:
  - Standard yEnc structure and compatibility
  - Authenticated encryption with integrity protection
  - Deterministic key and nonce derivation from password
  - Clear indication of encryption through yEnc control lines
  - Decoupled wire decryption from archive extraction passwords
  - Safe downstream handoff to assemblers and repair tools

It is intended for use in binary file uploads where payload confidentiality
and transport integrity are required across Usenet distribution networks.

----------------------------------------------------------------------
2. Definitions

  yEnc Block:
    A text segment beginning with "=ybegin" and ending with "=yend".

  yEnc Control Line:
    Any line within a yEnc block that begins with "=y" (such as
    "=ybegin", "=ypart", "=yend", or "=yencryption").

  Data Line:
    Any line within a yEnc block that does not begin with "=y"
    (contains the actual encoded binary data).

  Binary Payload:
    The original binary file data before any encryption or yEnc
    encoding.

  Encrypted Payload (Ciphertext):
    The binary data after XChaCha20-Poly1305 encryption, excluding the
    128-bit authentication tag which is carried in the =yencryption header.

  segmentIndex:
    An unsigned 32-bit integer in the range 1..=4294967295 carried
    in the article bootstrap (the index parameter of =yencryption and
    bytes 16..19 of Line 1 prefix). It provides unique nonce values
    for every segment across the upload session without file-boundary
    arithmetic or NZB XML dependencies.

  yenc_encrypted Provenance:
    An explicit metadata flag in the NZB <head> section defined as
    <meta type="yenc_encrypted">true</meta>. It indicates that the
    underlying yEnc articles are wire-encrypted and instructs download
    clients to dispatch them to the transport decryption engine.

  Dual-Bootstrap Agreement:
    When control line encryption and body encryption are combined,
    the 16-byte raw salt and 4-byte uint32_be segmentIndex from Line 1
    MUST match the salt and index parameters encoded in the =yencryption
    header byte-for-byte and value-for-value. Because the two standards
    share one salt value, the combined-mode salt MUST lie in the
    intersection of the two salt domains, which is the control standard's
    253-byte Alphabet: every shared salt byte MUST differ from 0x00,
    0x0A, and 0x0D.

----------------------------------------------------------------------
3. Processing Procedure

Encryption Input: Binary file data, password, and the segmentIndex assigned
to the segment.

Encryption and decryption follow the authoritative procedures: Section 4
defines the encryption algorithm, including key and nonce derivation and the
canonical =yencryption header grammar. Section 5 defines the decryption
procedure and error handling.

Header placement: for single-part articles, =yencryption is physical
line 2, immediately following =ybegin. For multipart articles, =ypart
is physical line 2 and =yencryption is physical line 3, immediately
following =ypart. The header references the segmentIndex assigned to
the segment.

Article bootstrap layout: the Line 1 prefix is a fixed 20-byte sequence,
16 raw salt bytes at offsets 0..15 followed by uint32_be(segmentIndex) at
offsets 16..19 (the exact layout defined by the control lines standard).
The same salt value is what the =yencryption salt parameter encodes, and
the same segmentIndex value is what the =yencryption index parameter
encodes; see the Dual-Bootstrap Agreement.

Combined mode order of operations: when control line encryption is also
applied, the =yencryption line is itself a yEnc control line and arrives
FF1-encrypted. A decoder MUST restore control lines first, using the
control lines standard, and MUST validate the five-token =yencryption
grammar and dual-bootstrap agreement only after that restoration. A
decoder that expects a plaintext =yencryption token sequence directly on
the wire is non-conformant in combined mode.

----------------------------------------------------------------------
4. Encryption Algorithm

Algorithm: XChaCha20-Poly1305 (RFC 8439 Extended)

Parameters:
  - Cipher: XChaCha20 (256-bit key, 192-bit nonce)
  - Authentication: Poly1305 (128-bit tag)
  - Salt: 16-byte random value over the full byte domain 0x00..0xFF
    (generated via cryptographically secure RNG). In body-only mode the
    salt is not restricted to the 253 Alphabet bytes. In combined mode
    (control line encryption also applied) the single shared salt MUST lie
    in the intersection of the two domains, which is the control standard's
    253-byte Alphabet: every salt byte MUST differ from 0x00, 0x0A, and 0x0D
    so that the byte-for-byte dual-bootstrap equality in the control
    standard is satisfiable. A producer that samples a forbidden byte for
    the shared salt cannot satisfy both standards and MUST resample.
  - Key derivation: Argon2id(password, salt, time=1, memory=64MB,
    threads=4, 256-bit output)
  - Nonce derivation: HMAC-SHA256(key, "yenc-body nonce" ||
    uint32_be(segmentIndex))[0:24]
    where segmentIndex is the unsigned 32-bit integer in range 1..=4294967295
    encoded as a 4-byte unsigned integer in big-endian order (uint32_be,
    network byte order).

Procedure:

  a. Generate salt = Random 16-byte value (once per upload session,
     use cryptographically secure RNG).
  b. Derive key = Argon2id(password, salt, time=1, memory=64MB,
     threads=4, 256-bit output).
  c. Derive nonce = HMAC-SHA256(key, "yenc-body nonce" ||
     uint32_be(segmentIndex))[0:24].
     The message input to HMAC-SHA256 is an exact 19-byte sequence:
     - Bytes 0..14 (15 bytes): ASCII prefix "yenc-body nonce"
       (0x79 0x65 0x6e 0x63 0x2d 0x62 0x6f 0x64 0x79 0x20 0x6e
        0x6f 0x6e 0x63 0x65)
     - Bytes 15..18 (4 bytes): uint32_be(segmentIndex), serialized
       as a fixed 4-byte unsigned integer in big-endian order
       (network byte order: (segmentIndex >> 24) & 0xFF,
        (segmentIndex >> 16) & 0xFF, (segmentIndex >> 8) & 0xFF,
        segmentIndex & 0xFF).
     The first 24 bytes (digest[0..24]) of the resulting 32-byte
     HMAC-SHA256 digest are extracted as the 192-bit nonce for
     XChaCha20.
  d. Encrypt binary payload using XChaCha20-Poly1305 with derived
     key and nonce, producing ciphertext and 128-bit authentication
     tag.
  e. Apply yEnc encoding to the ciphertext only (excluding the tag).
  f. Insert the =yencryption header defined below.

Canonical =yencryption Grammar:
The following ABNF defines the complete line content. SP and DIGIT are
imported from RFC 5234. A line terminator is not part of the grammar.

    yencryption = "=yencryption" SP
                  "cipher=XChaCha20-Poly1305" SP
                  "salt=" 32HEXDIG-LOWER SP
                  "index=" 8HEXDIG-LOWER SP
                  "tag=" 32HEXDIG-LOWER
    HEXDIG-LOWER = DIGIT / %x61-66

The resulting line has exactly five SP-separated tokens in this order:

  =yencryption cipher=XChaCha20-Poly1305 salt=<32_hex_chars> index=<8_hex_chars> tag=<32_hex_chars>

Each placeholder denotes lowercase hexadecimal characters and is replaced by
the encoded value: salt is exactly 32 hex chars, index is exactly 8 hex chars
representing uint32_be(segmentIndex) in range 00000001..ffffffff (00000000 is invalid),
and tag is exactly 32 hex chars. The angle brackets and placeholder text do not
appear on the wire. Total line content is exactly 128 bytes (ASCII characters),
measured after NNTP dot-unstuffing and excluding any line terminator (CRLF or
bare LF).
A producer MUST emit exactly one SP between tokens and no leading or trailing
whitespace. A consumer MUST reject tabs, repeated spaces, reordered, duplicate,
missing, or extra fields, uppercase hexadecimal digits, non-hexadecimal characters,
values of any other length, and any cipher name other than XChaCha20-Poly1305.

Single-part yEnc blocks MUST place =yencryption at physical line 2 immediately
after =ybegin. Multipart yEnc blocks MUST place =ypart at physical line 2 and
=yencryption at physical line 3 immediately after =ypart. A consumer MUST
reject multiple =yencryption lines in one article.

----------------------------------------------------------------------
5. Decryption and Error Handling

Input: Fetched yEnc block with encrypted binary data, password from the
NZB metadata.

Decryption Processing:

1. Parse the yEnc block and locate the =yencryption header at line 2
   (single-part) or line 3 (multipart). A missing, incomplete, or truncated
   =yencryption line at the expected position is provider corruption (see
   the retriable tier below), not a structural failure; the failure classes
   are named by the malformed-input taxonomy (for example MISPLACED_
   ENCRYPTION_HEADER or LINE_TRUNCATED) and retry is permitted.
2. Validate that the line conforms strictly to the five tokens grammar
   with cipher=XChaCha20-Poly1305, valid lowercase 32-hex salt, valid
   lowercase 8-hex index (non-zero), and valid lowercase 32-hex tag.
   The line content must be exactly 128 bytes (ASCII characters) excluding
   line terminators (CRLF or bare LF); a shorter or longer line fails the
   grammar check as a truncation or extension defect and MUST be treated
   as provider corruption.
3. In dual-encrypted mode, assert that the 16-byte decoded salt equals
   the restored Line 1 raw salt, and the decoded index equals the restored
   Line 1 segmentIndex. If unequal, fail closed with PROVIDER_FAILOVER
   (the retriable tier defined below): mark the article corrupt and try an
   eligible alternate provider.
4. Decode yEnc data lines to extract ciphertext bytes.
5. Verify wire CRC against ciphertext bytes if present in =yend. The wire
   CRC is computed over the decoded ciphertext bytes, never over plaintext.
   CRC verification MUST precede AEAD authentication, and passing the CRC
   check confers no permission to release bytes: the zero-output rule below
   remains in force until authentication succeeds.
6. Derive key and nonce using password, salt, and segmentIndex (uint32_be).
7. Authenticate and decrypt ciphertext using XChaCha20-Poly1305. If
   authentication fails, no CRC result observed in step 5 changes the
   outcome: the article fails as provider corruption.
8. On authentication success, discard or clear wire CRC metadata
   (crc32 = None) and forward decrypted plaintext to assembly/PAR2.

Two-Tier Error Classification:

An implementation MUST classify a failure by the input that failed validation.
The structural tier applies to NZB metadata and configuration obtained before
an article fetch. The provider-corruption tier applies to bytes in a fetched
article after those structural inputs have passed validation. A malformed,
missing, or misplaced control line in the fetched article is therefore
provider corruption, including malformed =yencryption syntax, an unsupported
cipher token, a duplicate =yencryption line, and a dual-salt or dual-index mismatch.
This rule prevents the same article defect from being classified in both tiers.

1. Non-Retriable Structural Failures:
   - Missing NZB provenance when transport decryption was requested.
   - Malformed NZB XML.
   - Missing or empty password in NZB metadata.
   - Locally unsupported encryption mode or cryptographic dependency.
   Action: Abort the job without querying alternate Usenet servers.
   Output: Zero bytes of plaintext and zero bytes of ciphertext.

2. Retriable Provider Corruption Failures:
   - Missing, malformed, misplaced, or duplicate yEnc control lines in the
     fetched article, including =ybegin, =ypart, =yencryption, and =yend.
   - An =yencryption line that violates the canonical grammar or contains an
     unsupported cipher token other than XChaCha20-Poly1305.
   - Dual-salt or dual-index mismatch between restored Line 1 and =yencryption.
   - Wire CRC mismatch over decoded ciphertext.
   - Poly1305 authentication tag verification failure.
   - Truncated or corrupted article body bytes.
   Action: Mark the article corrupt and try an eligible alternate provider.
   After all eligible providers fail, mark the segment failed so normal repair
   policy can run.
   Output: Zero bytes of plaintext and zero bytes of ciphertext.

Zero-Output Rule:
Decoders and download clients MUST NOT release or write unauthenticated
plaintext or ciphertext to a target file, cache visible to downstream stages,
or subsequent pipeline stage. Release means any transfer of those bytes to
another component, stream, pipe, buffer shared with another stage, or
observable sink, not only the final file write. Partial release during
decryption, before authentication completes, is a violation of this rule.
An implementation MAY retain article-sized working buffers until validation
completes and MUST discard them on failure.

----------------------------------------------------------------------
6. Length Properties

- Encrypted binary data has the exact same length as original binary payload
  (Poly1305 authentication tag is stored in the header, not in payload).
- yEnc encoding adds standard yEnc overhead (~1-2% typical expansion).
- Exactly one =yencryption control line of length 128 characters is added to
  the yEnc block header.
- The size parameter in =ybegin and =yend reflects the ciphertext size,
  which is identical to original plaintext size.

----------------------------------------------------------------------
7. Security Considerations

- XChaCha20-Poly1305 provides AEAD confidentiality and authenticity.
- Unique nonces derived per segmentIndex guarantee nonce uniqueness across
  all segments in the upload session.
- Argon2id with 16-byte random salts protects against brute-force and
  rainbow table attacks.
- Dual-bootstrap verification prevents salt or index substitution attacks
  across control line and body encryption schemes.
- Wire CRC verification confirms transport integrity before AEAD
  authentication; Poly1305 confirms cryptographic authenticity.
- Decoupled CRC metadata prevents downstream integrity tools (PAR2) from
  evaluating wire ciphertext CRCs against plaintext payloads.
- Subject lines, filenames, XML element order, and NNTP header order have
  no cryptographic role, enabling full subject and metadata obfuscation.
- All failure paths enforce zero output, preventing chosen-ciphertext
  or partial-plaintext leakage.

8. NZB File Requirements

An NZB document accompanying encrypted uploads MUST specify encryption
metadata according to the following rules:

Provenance Metadata Marker:
Encrypted NZBs MUST include in the <head> element:
  <meta type="yenc_encrypted">true</meta>
This tag indicates that articles are encrypted with yEnc transport
encryption. Downloaders use this marker to dispatch articles to the
transport decryption pipeline. If this tag is missing, downloaders treat
the NZB as standard unencrypted yEnc for backward compatibility.

Password Metadata:
The NZB file provides the encryption password via:
  <meta type="password">your_encryption_password</meta>
The password in this tag is used to derive the transport decryption key.
It MAY also be utilized by post-processing tools as the archive extraction
password for RAR/7z/ZIP archives if archive passwords match.

Standard NZB 1.1 Segments (Clean Segments):
Every <segment> element under <segments> within <file> uses standard NZB 1.1
attributes only:
  <segment bytes="750000" number="1">article-1@example.com</segment>
No custom segmentIndex XML attribute is emitted by uploaders or expected
by downloaders. Segment identity is fully self-describing in article bootstrap
bytes.

Producer Requirements:
For an encrypted upload, the NZB writer MUST:
1. Emit <meta type="yenc_encrypted">true</meta> in the <head> section.
2. Emit <meta type="password">...</meta> with the transport password.
3. Emit standard NZB 1.1 <segment> elements with bytes and number attributes only.
4. Embed the 1-based segmentIndex into the article bootstrap (Line 1 prefix
   and =yencryption index parameter).
5. Ensure each encrypted article has a unique segmentIndex within the upload session.
6. Assign indices continuously starting from 1 for fresh uploads.
7. Preserve an article's assigned index across retries, reposts, and resume.

Consumer Requirements:
An encryption-aware NZB reader MUST:
1. Inspect <head> for <meta type="yenc_encrypted">true</meta>.
2. Read <meta type="password"> for the transport password.
3. Treat <segment> elements as standard NZB 1.1 records without expecting
   custom XML attributes.
4. Extract segmentIndex and salt directly from fetched article bootstrap bytes.
5. Use the extracted segmentIndex for body nonce derivation.

Decoupling of Presentation Metadata:
- <file subject> has no cryptographic meaning.
- NNTP Subject headers have no cryptographic meaning.
- XML file order and segment order have no cryptographic meaning.
- Subject obfuscation does not impair decryption.

9. Interoperability & Transport Considerations

- Physical Line Indexing: Line indices are counted on 1-based physical
  lines after NNTP dot-unstuffing has been applied.
- Line Terminators: Canonical yEnc generators emit CRLF (0x0D 0x0A).
  Decoders MUST accept both CRLF and bare LF (0x0A) transparently.
- Article-Bounded Memory: This wire format requires authentication before
  plaintext release, so an implementation MAY buffer one complete article.
  It MUST keep working memory proportional to the configured maximum article
  size, O(article_size), and MUST NOT accumulate a complete multipart file or
  release in memory. Reference implementations accept typical article sizes
  from 128 KiB through 4 MiB and enforce local safety limits up to 8 MiB.
  These sizes are implementation guidance, not wire-format limits. A receiver
  MAY reject an article above its configured limit before allocation or
  decryption.
- Downstream CRC Normalization: After successful Poly1305 verification,
  decoders MUST clear or ignore wire CRC metadata (setting crc32 = None)
  so subsequent assembly and PAR2 tools compute fresh CRCs over plaintext.

10. Example

Input binary data: [18 bytes: 0x48656C6C6F20576F726C642E747874FF]
Password: "test123"

Corresponding Clean NZB 1.1 XML:

<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE nzb PUBLIC "-//newzBin//DTD NZB 1.1//EN" "http://www.newzbin.com/DTD/nzb/nzb-1.1.dtd">
<nzb xmlns="http://www.newzbin.com/DTD/nzb/nzb-1.1.dtd">
  <head>
    <meta type="yenc_encrypted">true</meta>
    <meta type="password">test123</meta>
  </head>
  <file poster="uploader@example.com" date="1758998400" subject="test upload [1/1] - file.bin yEnc (1/1)">
    <groups>
      <group>alt.binaries.test</group>
    </groups>
    <segments>
      <segment bytes="18" number="1">article-1@example.com</segment>
    </segments>
  </file>
</nzb>

Derived parameters:
- salt: 1a2b3c4d5e6f7890abcdef1234567890 (16 raw bytes)
- key: Argon2id("test123", salt, time=1, memory=64MB, threads=4, 256-bit)
- nonce: HMAC-SHA256(key, "yenc-body nonce" || uint32_be(1))[0:24]
  (where uint32_be(1) = 0x00 0x00 0x00 0x01)

Single-Part yEnc Encoded Wire Block (Line 2 Placement):

  =ybegin line=128 size=18 name=file.bin
  =yencryption cipher=XChaCha20-Poly1305 salt=1a2b3c4d5e6f7890abcdef1234567890 index=00000001 tag=a1b2c3d4e5f6789a0b1c2d3e4f567890
  <yEnc-encoded ciphertext data lines>
  =yend size=18 crc32=d4a1b2c3

Multipart yEnc Encoded Wire Block (Line 3 Placement):

  =ybegin part=1 total=2 line=128 size=36 name=file.bin
  =ypart begin=1 end=18
  =yencryption cipher=XChaCha20-Poly1305 salt=1a2b3c4d5e6f7890abcdef1234567890 index=00000001 tag=a1b2c3d4e5f6789a0b1c2d3e4f567890
  <yEnc-encoded ciphertext data lines>
  =yend size=18 part=1 pcrc32=d4a1b2c3

Decryption follows the authoritative procedure in Section 5: parse NZB
metadata and detect <meta type="yenc_encrypted">true</meta>, locate the
=yencryption header at line 2 (or line 3 if =ypart is line 2), verify the
exact five tokens with lowercase hexadecimal salt, 8-hex index, and tag,
decode data lines and verify wire CRC, derive key and nonce using the
extracted index (segmentIndex=1), execute XChaCha20-Poly1305, then clear
wire CRC metadata (crc32 = None) and release the original 18-byte binary
plaintext.

----------------------------------------------------------------------
11. Summary

This Standard describes authenticated encryption using XChaCha20-Poly1305
applied to binary payloads before yEnc encoding. It establishes:
  - Robust AEAD protection with zero output on failure.
  - Decoupled NZB transport provenance via <meta type="yenc_encrypted">true</meta>.
  - Exact header placement for single-part (line 2) and multipart (line 3).
  - Canonical five-token =yencryption grammar with fixed 128-character length.
  - Dual-bootstrap agreement between control line and body encryption.
  - Downstream CRC normalization for seamless assembly and PAR2 verification.
  - Two-tier error handling distinguishing retriable provider corruption
    from fatal structural faults.
