RFC-DRAFT: yEnc Control Lines Encryption Standard
Version: 0.3
Date: 2025-10-26
Author: Independent Specification

Status: Experimental
Category: Informational

Abstract:
This document defines a reversible, format-preserving encryption
scheme for yEnc control lines in yEnc-encoded binary blocks used in
Usenet transfers. The scheme maintains exact length and preserves the
printable yEnc character range required for Usenet transmission.

1. Scope

This specification describes the method to encrypt and decrypt
yEnc header and footer lines (lines beginning with "=y") while
maintaining:
  - yEnc-compatible printable characters
  - deterministic reconstruction of the original yEnc structure
  - exact length preservation for lines 2..N, with the first encrypted
    control line (lineIndex=1) expanding by exactly 16 bytes due to
    prepended random salt
  - data lines remain completely untouched in length and byte content
  - format-preserving output suitable for Usenet transmission
  - no additional yEnc encoding step required after encryption

It is intended for use in single or multipart binary uploads or
segment encryption, where yEnc control lines are encrypted while
preserving the overall yEnc structure and leaving data lines
unmodified. The overall yEnc block length increases by exactly 16 bytes
due to the salt prepended to the first line.

----------------------------------------------------------------------
2. Definitions

  yEnc Block:
    A text segment beginning with "=ybegin" and ending with "=yend".

  yEnc Control Line:
    Any line within a yEnc block that begins with "=y" (such as
    "=ybegin", "=ypart", "=yend", or custom lines such as
    "=yencryption").

  Data Line:
    Any line within a yEnc block that does not begin with "=y"
    (contains the actual encoded binary data).

  Line Content:
    The text content of a line excluding any trailing LF (0x0A) or
    CRLF (0x0D 0x0A) line terminators.

  Alphabet:
    The 253-symbol byte domain: all byte values 0x01–0xFF except
    0x0A (LF) and 0x0D (CR).

    Canonical Numeral Bijection Table (Radix 253):
    To ensure cross-language interoperability, each byte b in Alphabet
    maps to an integer numeral I in [0, 252] strictly by ascending
    byte value:
      - For b in [0x01, 0x09] (9 values):   I = b - 1  (I in [0, 8])
      - For b = 0x0B (VT):                  I = 9
      - For b = 0x0C (FF):                  I = 10
      - For b in [0x0E, 0xFF] (242 values): I = b - 3  (I in [11, 252])

    Reverse Mapping (numeral I in [0, 252] to byte b in Alphabet):
      - For I <= 8:                         b = I + 1
      - For I = 9:                          b = 0x0B
      - For I = 10:                         b = 0x0C
      - For I >= 11:                        b = I + 3

  segmentIndex:
    A 32-bit unsigned integer >= 1 providing a continuous, globally
    unique index across all segments in the upload sequence,
    regardless of file boundaries. For example, if file 1 has
    segments 1, 2, and 3, then segment 1 of file 2 has segmentIndex
    4. This ensures unique tweak values for every segment across the
    entire upload session.

  lineIndex:
    A 32-bit unsigned integer (1 <= lineIndex <= N) representing the
    1-based physical line number of every line (header, data, or
    footer) within the yEnc block, where N is the total physical line
    count of the block.
    Every line in the block—whether an encrypted control line or an
    unmodified data line—increments lineIndex sequentially by 1.
    The first line of the block has lineIndex = 1; the final footer
    line (=yend) has lineIndex = N.
    Used to generate unique tweaks for FF1 encryption/decryption of
    yEnc control lines.

----------------------------------------------------------------------
3. Processing Procedure

Input: Complete yEnc block with any line endings (LF or CRLF).

yEnc Structure Pattern:
- Header line(s): "=ybegin ...", "=ypart ..." (if multipart), "=yencryption ..." (if body encrypted)
- Data lines: encoded binary data (multiple lines)
- Footer line: "=yend ..."

Encryption Steps:

1. Split the yEnc block into individual lines, preserving line
   ending information for reconstruction.
2. Initialize lineIndex = 1.
3. Process lines sequentially, increment lineIndex sequentially on every physical line:
   a. For lines beginning with "=y":
      - Extract line content (excluding terminators)
      - Encrypt line content using FF1 with lineIndex-specific tweak
      - For lineIndex=1 (the first line): prepend the 16-byte salt to
        the ciphertext
      - Replace original line content with encrypted content (including
        prepended salt for line 1)
   b. For lines not beginning with "=y":
      - Leave data line content untouched
   c. Increment lineIndex by 1 for the next physical line (whether control
      or data line)
4. Preserve all line terminators and data lines exactly as received.

This approach encrypts yEnc control information (headers/footers)
while preserving data line integrity and overall structure.

----------------------------------------------------------------------
4. Encryption Algorithm

Algorithm: FF1 (NIST SP 800-38G compliant Format-Preserving
Encryption)

Parameters:
  - Alphabet: 253 printable characters (see Section 2)
  - Block cipher: AES-256
  - Salt: Random 16 byte value from alphabet  (use cryptographically
    secure RNG)
  - Key derivation: Argon2id(password, salt, time=1, memory=64MB,
    threads=4, 256-bit output)
  - Tweak: HMAC-SHA256(master, "yenc-control tweak" ||
    segmentIndex || lineIndex)[0:8]

Procedure (applied to each yEnc control line individually):

  a. Generate salt = Random 16 byte value from alphabet (once pe
     upload session, use cryptographically secure RNG)
  b. Derive masterKey = Argon2id(password, salt, time=1, memory=64MB,
     threads=4, 256-bit output)
  c. Derive encKey = HMAC-SHA256(masterKey, "yenc-control key")
  d. Derive tweak = HMAC-SHA256(masterKey, "yenc-control tweak" ||
     segmentIndex || lineIndex)[0:8] where lineIndex is the
     sequential index of the current line within the segment.
  e. Encrypt the line content using FF1 over the 253-character
     alphabet.
  f. For the first line (lineIndex=1): prepend the 16-byte salt to
     the encrypted content.
  g. Replace the original line content with the encrypted content
     (including salt for first line).

The encrypted control lines remain yEnc-compatible and require no
additional encoding step before transmission.

----------------------------------------------------------------------
5. Decryption Algorithm

Input: yEnc block with encrypted control lines (total physical lines N).

Steps:

1. Split the yEnc block into individual lines, preserving line
   endings.
2. Process line 1 (lineIndex=1) to extract salt:
   a. Extract line 1 content (excluding line terminators)
   b. Extract 16-byte salt from the first 16 bytes of line 1
   c. Remove salt prefix from line 1 content (remaining bytes are
      the FF1 ciphertext)
   d. Derive masterKey, encKey, and tweak using extracted salt,
      segmentIndex, and lineIndex=1
   e. Apply FF1 decryption over the 253-character alphabet
   f. Verify decrypted content starts with "=ybegin"
   g. Replace line 1 encrypted content with decrypted content
3. Process subsequent header lines (lineIndex = 2, 3, ...):
   a. For each physical line before data lines (lineIndex=2, 3, ...):
      - Extract line content (excluding line terminators)
      - Derive tweak using extracted salt, segmentIndex, and current lineIndex
      - Apply FF1 decryption over the 253-character alphabet
      - If decrypted content starts with "=y":
        * Replace line content with decrypted content
        * Continue to next line (increment lineIndex by 1)
      - If decrypted content does not start with "=y":
        * This line is the first data line (lineIndex = D)
        * Restore original line content untouched
        * Stop header decryption loop
4. Pass through data lines (lineIndex = D through N - 1):
   - Leave all data lines untouched, incrementing lineIndex for each physical line
5. Process the final line (footer, lineIndex = N):
   a. Extract the last physical line content (excluding line terminators)
   b. Derive tweak using extracted salt, segmentIndex, and lineIndex = N
   c. Apply FF1 decryption over the 253-character alphabet
   d. Verify decrypted content starts with "=yend"
   e. Replace line N encrypted content with decrypted content
6. Reconstruct the complete yEnc block with original line endings.

----------------------------------------------------------------------
6. Length Properties

- The first encrypted yEnc control line (lineIndex=1) expands by
  exactly 16 bytes due to the prepended random salt.
- All subsequent encrypted yEnc control lines (lineIndex > 1) preserve
  exact plaintext length (identical length to original).
- Data lines remain completely unchanged in length, byte content,
  and line terminators.
- Overall yEnc block length increases by exactly 16 bytes (the salt).
- Line endings (CRLF or LF) and data line formatting are preserved
  throughout the process.

----------------------------------------------------------------------
7. Security Considerations

- FF1 provides confidentiality equivalent to AES-256 under unique
  key/tweak pairs.
- The tweak ensures uniqueness per segmentIndex across all files.
- Argon2id with random salts provides strong protection against both
  brute-force and rainbow table attacks.
- Random salt per upload session ensures unique keys even for
  identical passwords across different uploads.
- The scheme offers confidentiality only, not integrity or
  authenticity.
- Deterministic output leaks identical plaintext segments if
  key/tweak pairs repeat.

----------------------------------------------------------------------
8. NZB File Requirements

When uploading encrypted yEnc blocks, Usenet upload tools MUST
include the file numbering information used for the calculation of
the continuous segmentIndex in the NZB file to preserve multipart
file reconstruction capability:

- The subject parameter of each <file> tag MUST begin with the file
  number specifier in the format "[<file number>/<total files>]"
- Example: subject="[1/3] filename.bin" for the first file of three
- This ensures download clients can determine the file number for
  the calculation of the continuous segmentIndex

- The NZB file CAN include the encryption password as a meta tag:
  <meta type="password">your_encryption_password</meta>
- This allows download clients to automatically decrypt the yEnc
  control lines

Usenet download clients encountering encrypted yEnc headers MUST:
- Extract the file number from the NZB subject line
- Use this information for proper file sequencing and calculation of
  the segmentIndex

This requirement ensures multipart file downloads work correctly even
when yEnc control lines are encrypted.

9. Interoperability Notes

- Any FF1 implementation conforming to NIST SP 800-38G may be used
  if it supports custom alphabets.
- Implementations MUST use the canonical 253-byte Alphabet numeral
  bijection specified in Section 2:
    Mapping byte octets b to numerals I in [0, 252]:
      - For b in [0x01, 0x09]:   I = b - 1  (numerals 0..8)
      - For b = 0x0B:            I = 9
      - For b = 0x0C:            I = 10
      - For b in [0x0E, 0xFF]:   I = b - 3  (numerals 11..252)
    Reverse mapping numerals I in [0, 252] to byte octets b:
      - For I <= 8:              b = I + 1
      - For I = 9:               b = 0x0B
      - For I = 10:              b = 0x0C
      - For I >= 11:             b = I + 3

10. Example

Input plaintext:

  =ybegin line=9 size=18 name=file.bin\r\n
  abcDEF123\r\n
  ghiJKL456\r\n
  =yend size=18\r\n

Encryption Processing:
- Total physical lines N = 4.
- Line 1 (lineIndex=1): "=ybegin line=9 size=18 name=file.bin" (33 bytes)
  -> FF1 encrypt with tweak(segmentIndex, 1) (33 bytes)
  -> Prepend 16-byte random salt from Alphabet
  -> Encrypted line 1 expands by 16 bytes: 16 bytes salt + 33 bytes ciphertext = 49 bytes.
- Line 2 (lineIndex=2): "abcDEF123" -> unchanged (data line).
- Line 3 (lineIndex=3): "ghiJKL456" -> unchanged (data line).
- Line 4 (lineIndex=4): "=yend size=18" (13 bytes)
  -> FF1 encrypt with tweak(segmentIndex, 4) (13 bytes)
  -> Preserves exact length: 13 bytes ciphertext.

Encrypted output:

  <16-byte salt>K7mX9pL2qR8vN4wZ6tY1uI5eA3cS0fH7j\r\n
  abcDEF123\r\n
  ghiJKL456\r\n
  T8nB2hM6xV9qL\r\n

Decryption Processing:
- Line 1 (lineIndex=1):
  * Extract first 16 bytes as salt.
  * Decrypt remaining 33 bytes with lineIndex=1 and extracted salt.
  * Result: "=ybegin line=9 size=18 name=file.bin" -> valid header, keep.
- Line 2 (lineIndex=2):
  * Attempt decrypt with lineIndex=2.
  * Result does not begin with "=y", indicating first data line.
  * Retain original "abcDEF123" untouched.
- Line 3 (lineIndex=3):
  * Data line -> retain original "ghiJKL456" untouched.
- Line 4 (lineIndex=4=N):
  * Decrypt last physical line (lineIndex=4) with extracted salt.
  * Result: "=yend size=18" -> valid footer.

After decryption, the reconstructed text matches the original yEnc
block exactly, with control lines restored and data lines unchanged.
Overall block length increased on wire by exactly 16 bytes due to salt
prepended to line 1.

----------------------------------------------------------------------
11. Summary

This Standard describes a deterministic format-preserving encryption
(FF1) applied selectively to yEnc control lines, producing
encrypted messages that:
  - Keep all data lines completely unchanged.
  - Encrypt only yEnc header/footer information (lines starting
    with "=y").
  - Preserve exact message structure and line endings.
  - Remain printable and safe for Usenet transport.
  - Require no additional yEnc encoding after encryption.

This approach provides targeted encryption of yEnc control information
while maintaining full compatibility with existing yEnc processing
tools.

This draft defines the canonical processing rules for interoperability
between implementations.
